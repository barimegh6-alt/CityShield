# CityShield — Project report

**Course:** B.Tech CS (AI & ML), Advanced Algorithms, CIA 3  
**Project:** Intelligent Smart City Emergency Response & Resource Optimization System  
*Team members, roll numbers and submission date: to be filled in by the team (not provided to the author of this build).*

## 1. Problem
During a city-scale emergency, operators must decide which incident to handle first, which team to send, how to move scarce supplies over a damaged road network, where coverage is missing, and in what order to deliver relief. These are classical algorithmic problems; CityShield solves each with a purpose-chosen algorithm implemented from scratch and shows its work in a web dashboard.

## 2. Scope
Eight modules over ten pages: dashboard, incident management, priority engine, team allocation, resource distribution, network connectivity, coverage planning, route optimisation, an algorithm lab and performance analytics. Data is synthetic; the system is an academic simulation, not an operational dispatch tool.

## 3. Technology
Java 17, Spring Boot 3.5, Spring Web, Spring Data JPA/Hibernate, MySQL 8, Bean Validation, JUnit 5/Mockito; React 18, Vite, Tailwind CSS, Recharts, Leaflet with OpenStreetMap tiles (the app degrades gracefully without tiles).

## 4. Design
Layered: controllers → services → pure-Java algorithm engine → repositories → MySQL (diagram in `README.md`; schema in `DATABASE_DOCUMENTATION.md`). The algorithm engine has no framework dependency, so it is unit-testable in isolation. Allocation and distribution follow **preview → commit**: previews are read-only; commits re-validate and write in one transaction. A seeded generator makes the data set reproducible.

## 5. Algorithms (summary)
| Module | Algorithm | Why this one |
|---|---|---|
| Priority | Binary max-heap | O(log n) re-prioritisation as incidents change |
| Connectivity | Disjoint Set Union | Fast component queries after road blocks |
| Inventory | Segment tree | O(log n) range sums and updates |
| Autocomplete | Trie | Cost depends on prefix, not on data size |
| Search | KMP | Linear-time text search with no backtracking |
| Distribution | Edmonds–Karp | Maximum supply delivered under road capacities |
| Team assignment | Kuhn matching | Maximum number of incidents covered |
| Coverage | Greedy set cover (vs exact) | NP-hard; ln n guarantee, checked against optimum |
| Routing | MST 2-approximation (vs nearest neighbour, Held-Karp) | Guaranteed ≤ 2 × optimal tour |
| Risk threshold | Randomized Quickselect | Expected O(n) percentile without sorting |

Full detail: `ALGORITHM_DOCUMENTATION.md`.

## 6. Data set
50 zones, 114 roads, 83 distribution edges, 18 centres, 15 hospitals, 40 teams, 10 resource types, 500 inventory rows, 1,000 incidents (145 active at seed time), 25 relief destinations. Generated by `data/tools/generate_dataset.py` with a fixed seed.

## 7. Results
Measured benchmarks are in `data/benchmarks/benchmark_results.csv` and summarised in `ALGORITHM_DOCUMENTATION.md`. Headline, honestly stated: at large inputs the custom heap, DSU, segment tree, trie, KMP and Quickselect beat their baselines (e.g. segment tree 1.4 ms vs 28 ms linear scan at 100,000 elements; Quickselect 11.9 ms vs 67.6 ms sorting 1,000,000 values). Edmonds–Karp, Kuhn matching and greedy set cover cost more time than naive baselines but produce better solutions (e.g. 2,983 vs 2,644 matches at 3,000 slots). Greedy set cover reached cost 31 against an exact optimum of 30 on the 18-set test. Nearest neighbour gave shorter tours than the 2-approximation in these runs; the approximation is chosen for its guarantee. Timings come from one sandbox machine; rerun on your own.

## 9. Known limitations
* The items marked "not run" above.
* Distances are Haversine × 1.3, not real road routing.
* Exact set cover is limited to 24 candidate centres, Held-Karp to 12 nodes.
* Critical-road detection is O(E·(V+E)) — adequate for 114 roads, not for very large networks.
* The priority heap lives in memory and is rebuilt from the database at start-up; it assumes a single backend instance.
* No authentication/authorisation: this is a single-user academic demo.
* Benchmark timings vary with hardware and JIT warm-up.
* Map tiles need internet; without it only data overlays are shown.

## 10. Future work
Real road-network routing, authentication, multi-instance priority queue (e.g. database-backed), streaming incident feeds, and a bigger exact set-cover solver (branch and bound).
